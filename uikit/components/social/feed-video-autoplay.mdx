**Key Benefit**: Members scroll past videos they never tap. With auto-play on, the most visible video in a feed plays in place, muted, so members get a preview of every video as they scroll and one tap takes them into the full player — with no feed or player code to write.
</Info>

## Overview

Feed video auto-play is built into the UIKit's post components. Once an admin turns it on for the network, every supported feed plays videos automatically: there is nothing to add to your screens. Members can choose when it runs for themselves, and an admin can turn it off for the whole network at any time.

## How it works

Auto-play runs only when **both** of these allow it. Neither one outranks the other: if either is off, nothing auto-plays.

| Control | Who sets it | Default |
| --- | --- | --- |
| **Network switch** | A network admin, through the API ([Turn it on for your network](#turn-it-on-for-your-network)) | **Off**. A switch that is missing or can't be read counts as off. |
| **Member setting** | Each member, in their own profile menu ([Member setting](#member-setting)) | **On** |

When both allow it, the UIKit behaves like this:

| Situation | What members see |
| --- | --- |
| A video is at least half on screen and nothing else is playing | It plays muted, at once |
| Two videos are equally visible | The higher one plays |
| The playing video drops below half | The most visible video takes over |
| The member unmutes | Every later video in the session plays with sound, including the full player |
| The member taps a playing video | The full player opens, already playing from the same point |
| A video ends | Its dimmed last frame with **Watch again**; it doesn't loop |
| The member scrolls back to a video | It resumes from where it stopped |
| A sheet, menu or the full player covers the feed, or the app or tab goes to the background | The video pauses, then resumes from the same point |
| The video is loading for more than a second | A spinner over the dimmed frame; the sound button keeps working |
| Playback fails, or auto-play can't run (switch off, member setting off, offline) | The thumbnail and play button |

Feed previews of live and recorded live posts are **not counted** as views. Counting starts when the member opens the live player.

### Where auto-play runs

| Auto-plays | Shows the thumbnail and play button |
| --- | --- |
| Global and For You feeds, community feeds (including pinned and announcement posts), the community **Pin** tab, user feeds, event discussions, post detail | Search results, pending posts, community **Videos** and **Livestream** tabs, media galleries |

Video, clip, live and recorded live posts all auto-play, including videos inside a carousel: swiping to a video page plays it.

## Turn it on for your network

Auto-play is **off by default**. A network admin turns it on with the network feed setting API, using an [admin token](/analytics-and-moderation/social+-apis-and-services/network-settings). There is no console toggle for it yet.

```bash
curl -X PUT "https://api.{API_REGION}.amity.co/api/v3/network-settings/feed-setting" \
  -H "Authorization: Bearer <ADMIN_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{ "post": { "video": { "autoPlay": true } } }'
```

Send `"autoPlay": false` to turn it off again.

<Note>
Only an admin can change the switch. A request with a user token is rejected with `403`.
</Note>

Members' apps pick up a change the next time their SDK session is established: at login, at a cold start or after a reconnect. Switching back to the app or tab does not re-read it.

## Read the switch in your app

The UIKit reads the network switch for you. Read it yourself only when you build your own video UI and want it to follow the same switch. The value is on the post feed's video content setting, and is `false` when the network has never set it.

<CodeGroup>

```kotlin Android
AmityCoreClient.getContentCheck()
    .map { contentCheck -> contentCheck.post()?.video?.autoPlay ?: false }
    .doOnSuccess { isAutoPlayOn ->
        if (isAutoPlayOn) {
            startFeedPreviews()
        }
    }
    .doOnError { error ->
        handleGeneralError(error)
    }
    .subscribe()
```

```swift iOS
let settings = try await client.getContentSettings()
let isAutoPlayOn = settings.post?.videoSettings?.autoPlay ?? false

if isAutoPlayOn {
    startFeedPreviews()
}
```

```tsx React
import { Client } from '@amityco/ts-sdk';

const feedSettings = await Client.getFeedSettings();
const isAutoPlayOn =
  feedSettings.post?.find(({ contentType }) => contentType === 'video')?.autoPlay ?? false;

if (isAutoPlayOn) {
  startFeedPreviews();
}
```

</CodeGroup>

| Platform | Method | Field |
| --- | --- | --- |
| Android | `AmityCoreClient.getContentCheck(): Single<AmityContentCheck>` | `post()?.video?.autoPlay: Boolean` |
| iOS | `client.getContentSettings() async throws -> AmityContentSettings` | `post?.videoSettings?.autoPlay: Bool` |
| TypeScript | `Client.getFeedSettings(): Promise<Amity.FeedSettings>` | `post` entry with `contentType: 'video'`, `autoPlay?: boolean` |

## Member setting

Members open **their own profile → ⋯ menu → Settings → Autoplay in feed**. The row shows the current choice. Visitors and bots don't see the row and always count as on.

| Platform | Opens as | Choices |
| --- | --- | --- |
| Android, iOS | A bottom sheet over the profile menu | **on Wi-Fi and mobile data** · **on Wi-Fi only** · **Never** |
| React Web | The **Autoplay in feed** page, with a description | An **On/Off** switch |

- A choice is saved as soon as it's made. On Android and iOS, tapping outside the sheet closes it.
- With nothing saved, auto-play is on: **on Wi-Fi and mobile data** on Android and iOS, **On** on Web.
- The choice is saved on the device (in the browser on Web), not per user. It carries over to whoever signs in next on that device or browser.
- On Android and iOS, Data Saver (Android) and Low Data Mode (iOS) also stop auto-play.
- The network switch off overrides any member choice.

<Note>
Web offers a single On/Off switch because browsers can't reliably tell Wi-Fi from mobile data. Web doesn't check the connection type or the browser's data saver, so **On** auto-plays on any connection.
</Note>

### Web: the setting page with your own navigation

If your web app passes `onChangePage` to `AmityUiKitProvider` to handle navigation itself, the **Autoplay in feed** row sends `{ type: 'AutoplaySettingPage' }` instead of opening the page. Render `AmityAutoplaySettingPage` for that type. It takes no props.

```tsx React
import { useState } from 'react';
import { AmityUiKitProvider, AmityAutoplaySettingPage } from '@amityco/ui-kit';

function App() {
  const [page, setPage] = useState<{ type: string } | null>(null);

  return (
    <AmityUiKitProvider
      /* your existing apiKey, apiRegion, userId and other props */
      onChangePage={(next) => setPage(next)}
    >
      {page?.type === 'AutoplaySettingPage' ? <AmityAutoplaySettingPage /> : <YourCurrentScreen />}
    </AmityUiKitProvider>
  );
}
```

Without `onChangePage`, the UIKit opens the page itself and you don't need any code.

## Customization

Feed video auto-play has no config IDs on Android or iOS, and none for the feed video on Web: the video, its sound button and **Watch again** can't be hidden or themed through config, so auto-play can't be turned off for a single screen. To turn it off, use the network switch.

The Web setting page has a page ID, like other Web pages:

| Config ID | Type | Description |
| --- | --- | --- |
| `autoplay_setting_page/*/*` | Page | You can customize the page theme (Web only) |
| `autoplay_setting_page/*/back_button` | Element | You can customize the back button icon (Web only) |
| `autoplay_setting_page/*/title` | Element | You can customize the title text (Web only) |

### Text

All three platforms use the same [localization](/uikit/customization/localization) keys:

| Key | Default (en) | Platforms |
| --- | --- | --- |
| `amity_social_feed_video_unmute` | Turn sound on | All |
| `amity_social_feed_video_mute` | Turn sound off | All |
| `amity_social_feed_video_replay` | Watch again | All |
| `amity_social_autoplay_setting_account_section` | Account | All |
| `amity_social_autoplay_setting_section` | Settings | All |
| `amity_social_autoplay_setting_row` | Autoplay in feed | All |
| `amity_social_autoplay_setting_wifi_and_data` | on Wi-Fi and mobile data | Android, iOS |
| `amity_social_autoplay_setting_wifi_only` | on Wi-Fi only | Android, iOS |
| `amity_social_autoplay_setting_never` | Never | Android, iOS |
| `amity_social_autoplay_setting_on` | On | Web |
| `amity_social_autoplay_setting_off` | Off | Web |
| `amity_social_autoplay_setting_web_description` | Automatically play videos in your feeds. These settings only apply when you use the website. | Web |

## Troubleshooting

<AccordionGroup>
  <Accordion title="Videos don't auto-play" icon="circle-pause">
    1. Check that the network switch is on: read it with [Read the switch in your app](#read-the-switch-in-your-app), or send the `PUT` above with `"autoPlay": true`.
    2. Members pick up a change only at their next session: sign out and back in, or restart the app.
    3. Check the member's own setting in **profile → ⋯ → Settings → Autoplay in feed**.
    4. On Android and iOS, check Data Saver or Low Data Mode, and **on Wi-Fi only** while on mobile data.
    5. Check that the screen is one where auto-play runs ([Where auto-play runs](#where-auto-play-runs)).
  </Accordion>
  <Accordion title="Web: every video shows a play button" icon="globe">
    Some browsers block auto-play entirely (for example Safari with **Never Auto-Play**, or Firefox with **Block Audio and Video**). When the browser refuses even muted playback, auto-play stays off for the session and every video shows its play button until the page reloads.
  </Accordion>
  <Accordion title="Web: the first video plays muted after the member turned sound on" icon="volume-xmark">
    Some browsers won't play sound without a fresh tap. The video then plays muted and its sound button shows muted; the member's next tap turns the sound back on.
  </Accordion>
</AccordionGroup>
