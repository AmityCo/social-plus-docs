## How Webhooks Work

<Info>
**Webhook vs Traditional API**: Unlike traditional APIs where your application makes requests to receive responses, webhooks are "reverse APIs" where social.plus initiates communication by sending data to your system as soon as events occur.
</Info>

### Event-Driven Architecture

<AccordionGroup>
  <Accordion title="Event Triggers">
    **Real-Time Delivery**
    - Events are triggered instantly when actions occur in your social.plus application
    - HTTP POST payloads sent to your configured webhook URLs
    - Near-real-time delivery for immediate response capabilities

    **Event Types**
    - User actions (posts, comments, reactions)
    - Chat messages and channel events
    - Community and social interactions
    - Moderation and safety events
  </Accordion>
  <Accordion title="Webhook Characteristics">
    **Performance Considerations**
    - Each webhook request times out after 1 second
    - With **Retry** on, a failed delivery is retried for up to 24 hours. See [Delivery and retries](#delivery-and-retries).
    - Your webhook endpoint must respond within this interval
    - System should return HTTP 200 status with empty JSON response

    **Reliability Features**
    - Automatic retry mechanisms for failed deliveries
    - Signature verification for security
    - Scalable infrastructure for high-volume events
  </Accordion>
</AccordionGroup>

## Delivery and retries

A short outage on your side does not have to cost you events. With **Retry** on, social.plus keeps sending a failed delivery for up to 24 hours, until your endpoint accepts it.

A delivery is one event sent to one webhook. A delivery succeeds when your endpoint returns a 2xx status within 1 second.

### Turn retry on or off

Each webhook has its own **Retry** setting. To change it, edit the webhook in **Settings → Webhook** in the console. When you add a webhook in the console, **Retry** is on.

- **Retry on:** we retry a failed delivery on the schedule in [When we retry](#when-we-retry).
- **Retry off:** we send each delivery once.

### What we retry

| Failure | Retried |
|---------|---------|
| No response within 1 second | Yes |
| The endpoint cannot be reached, for example because of a DNS, connection, or TLS error | Yes |
| HTTP `429` | Yes |
| HTTP `5xx` | Yes |
| Any other HTTP `4xx`, such as `400` or `404` | No |

We do not retry the other `4xx` statuses. Your endpoint rejected the request itself, so a retry would fail the same way.

### When we retry

1. We try up to 3 times in the first few seconds.
2. If those tries fail, we retry 1, 5, 15, and 30 minutes, then 1, 2, 4, 8, 16, and 24 hours after the quick tries end.

Each scheduled time can vary by up to 10%, so that the retries of many deliveries do not all arrive at once. No scheduled time is later than 24 hours after the quick tries end.

That makes up to 13 tries. The delivery ends at the first 2xx response. It also ends when a try fails in a way that we do not retry, such as a `400` response. The delivery then shows as **Failed**. If the last try fails, the delivery shows as **Retries exhausted**.

### What a retry sends

- **The same event.** A retry sends the same event payload as the first try.
- **The webhook's current settings.** A scheduled retry uses the URL, secret, and custom headers that the webhook has when the retry runs. We sign each retry with the webhook's current secret.
- **The same delivery ID.** See [Identify a delivery](#identify-a-delivery).

If you delete a webhook or turn its **Retry** off, we drop its waiting retries. The **Deliveries** tab shows each dropped delivery as **Failed**, with the reason "The webhook was deleted while it was waiting" or "Retry was turned off while it was waiting".

### Identify a delivery

Every request carries two headers that tell you which delivery it is and which try:

| Header | Value |
|--------|-------|
| `x-socialplus-delivery-id` | `<event ID>:<webhook ID>`, for example `23302103085264915:6af6f0430bab059f47f6c26b`. The value is the same on every try of a delivery. |
| `x-socialplus-delivery-attempt` | The try number, starting at `1`. The count includes the quick tries. |

We set these two headers after your custom headers. A custom header with the same name does not replace them.

### Handle retries in your endpoint

Your endpoint can receive the same delivery more than once. For example, this happens when your endpoint processed a delivery but responded after the 1-second timeout.

1. Respond with a 2xx status within 1 second. Process the event after you respond.
2. Verify `x-amity-signature` on every try, as described in [Signature verification](#signature-verification).
3. Store the `x-socialplus-delivery-id` of each delivery that you process. If a request has an ID that you already handled, respond with a 2xx status and skip it.
4. Do not rely on arrival order. A retry can arrive after newer events.

```javascript Node.js
const crypto = require('crypto');
const express = require('express');

const app = express();
const handled = new Set(); // In production, use a shared store with an expiry.

app.post('/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const expected = Buffer.from(
    crypto.createHmac('sha256', process.env.WEBHOOK_SECRET).update(req.body).digest('base64')
  );
  const received = Buffer.from(req.get('x-amity-signature') || '');
  if (received.length !== expected.length || !crypto.timingSafeEqual(received, expected)) {
    return res.sendStatus(401);
  }

  const deliveryId = req.get('x-socialplus-delivery-id');
  if (handled.has(deliveryId)) {
    return res.sendStatus(200); // A retry of a delivery you already handled.
  }
  handled.add(deliveryId);

  res.sendStatus(200); // Respond first, within 1 second.
  processEvent(JSON.parse(req.body)); // Your own processing.
});
```

### Monitor deliveries

The **Deliveries** tab in **Settings → Webhook** lists the deliveries of the last 3 days, with the result and the number of tries for each one. A delivery that waits for a retry shows a **Retrying** row with the time of the next try. To find one delivery, search by its `x-socialplus-delivery-id`. For details, see [Webhook deliveries](/analytics-and-moderation/console/settings/integrations#webhook-deliveries).

## Security and Authentication

### Signature Verification

<Warning>
**Security Requirement**: Always verify the `x-amity-signature` header before processing webhook events to prevent request forgery and ensure data integrity.
</Warning>

<Tabs>
  <Tab title="Header Details">
    ### Delivery Headers
    
    All webhook HTTP POST requests include these headers:

    | Header | Description |
    |--------|-------------|
    | `x-amity-signature` | HMAC Base64 digest of the response body using SHA-256 hash function |
    | `User-Agent` | Identifies the webhook delivery system |
    | `Content-Type` | Always `application/json` |
    | `Content-Length` | Size of the JSON payload |
    | `x-socialplus-delivery-id` | Identifies the delivery. The same on every try. See [Identify a delivery](#identify-a-delivery). |
    | `x-socialplus-delivery-attempt` | The try number, starting at `1` |
  </Tab>

  <Tab title="Legacy Support">
    ### Backward Compatibility
    
    <Info>
    **Legacy Header**: You may receive duplicate requests with `x-eko-signature` header for backward compatibility. You can safely ignore these requests and only process events with `x-amity-signature`.
    </Info>
    
    **Migration Approach**
    - Process events with `x-amity-signature` header
    - Ignore duplicate events with `x-eko-signature`
    - Update your systems to use the new signature format
  </Tab>
</Tabs>

## Best Practices

<CardGroup cols={2}>
  <Card title="Security" icon="shield">
    **Always Verify Signatures**
    - Implement signature verification for all webhooks
    - Use constant-time comparison to prevent timing attacks
    - Keep webhook secrets secure and rotate regularly
    - Log suspicious or invalid requests
  </Card>
  <Card title="Performance" icon="bolt">
    **Optimize Response Times**
    - Respond within 1 second to prevent timeouts
    - Process events asynchronously when possible
    - Implement proper error handling and logging
    - Monitor webhook performance and delivery rates
  </Card>
  <Card title="Reliability" icon="check">
    **Handle Failures Gracefully**
    - Implement retry logic for failed processing
    - Skip duplicate deliveries by `x-socialplus-delivery-id`
    - Store events for replay in case of system failures
    - Monitor webhook health and alert on issues
  </Card>
  <Card title="Scalability" icon="seedling">
    **Design for Scale**
    - Use queues for high-volume event processing
    - Implement rate limiting and backpressure handling
    - Scale webhook endpoints horizontally
    - Cache frequently accessed data
  </Card>
</CardGroup>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Common Issues">
    **Webhook Not Receiving Events**
    - Verify webhook URL is accessible from social.plus servers
    - Check firewall rules allow traffic from social.plus IP addresses
    - Ensure webhook endpoint responds with HTTP 200 status
    - Verify webhook is properly configured in admin panel

    **Signature Verification Failures**
    - Confirm you're using the correct webhook secret
    - Verify signature calculation matches expected format
    - Check for character encoding issues in payload
    - Ensure raw request body is used for signature verification
  </Accordion>
  <Accordion title="Performance Issues">
    **Timeout Problems**
    - Optimize webhook handler for sub-1 second response
    - Move heavy processing to background jobs
    - Implement proper database connection pooling
    - Add monitoring and alerting for response times

    **High Volume Handling**
    - Implement event queuing and batch processing
    - Scale webhook endpoints horizontally
    - Use caching for frequently accessed data
    - Consider implementing backpressure mechanisms
  </Accordion>
  <Accordion title="Debugging Tips">
    **Testing Webhooks**
    - Use tools like ngrok for local development testing
    - Implement comprehensive logging for webhook events
    - Test with different event types and payloads
    - Monitor webhook delivery success rates

    **Monitoring and Alerts**
    - Set up alerts for webhook failures
    - Monitor response times and error rates
    - Log all webhook events for debugging
    - Implement health checks for webhook endpoints
  </Accordion>
</AccordionGroup>
